# 交付、演示与验收方案

## 1. 标准交付包

### A. 解决方案说明

- 业务问题；
- 用户与使用场景；
- 输入、输出和边界；
- 架构与数据流；
- 风险、限制和伦理要求。

### B. 数据资产

- 原始数据来源清单；
- 数据字典；
- 脱敏样例；
- 数据质量报告；
- 数据许可与采集批次记录。

### C. 方法资产

- 特征注册表；
- 规则基线；
- 候选模型；
- 阈值与等级配置；
- 风险标签字典；
- 评分解释方法。

### D. 实验资产

- 固定数据划分；
- 训练与评估配置；
- 基线和候选方案对比；
- 指标、图表和原始结果；
- 典型正确/错误样本；
- 运行清单和随机种子。

### E. 软件与展示

- 一键运行入口；
- 示例输入和示例输出；
- 静态或交互式展示页面；
- 故障排查说明；
- 演示讲解脚本。

## 2. 推荐演示主线（8–12 分钟）

1. 说明平台评价数据为何不能直接等权使用；
2. 展示数据来源、字段和质量问题；
3. 展示一个高可信、一个证据不足、一个高风险样本；
4. 展示每个样本的分数、等级、置信度和风险证据；
5. 展示原始聚合评分与可信度修正评分的变化；
6. 展示规则基线与候选模型的比较；
7. 调整等级阈值，说明审核量与风险之间的取舍；
8. 说明系统不会直接处罚用户以及当前能力边界；
9. 给出可复现命令与交付文件位置。

## 3. 页面应围绕六个问题组织

1. 数据可靠吗？——数据来源和质量页；
2. 系统依据什么判断？——特征与方法页；
3. 效果如何？——实验与模型对比页；
4. 哪些数据有风险？——等级、标签和样本解释页；
5. 对业务有什么影响？——聚合修正与处置模拟页；
6. 能否复现和审计？——版本、配置和运行记录页。

如果现有页面只是按算法名称平铺，应增加一个“解决方案总览/决策驾驶舱”作为统一入口。

## 4. 验收清单

### 可运行性

- [ ] 新环境按 README 可完成安装；
- [ ] 一条命令可运行示例流水线；
- [ ] 一条命令可启动展示服务；
- [ ] 页面不依赖 `file://` 访问；
- [ ] 缺失数据时给出可操作错误，而不是只有 `Failed to fetch`。

### 数据与方法

- [ ] 输入字段、量表和缺失策略明确；
- [ ] 特征定义和版本可追踪；
- [ ] 数据划分无明显泄漏；
- [ ] 阈值不在测试集上选择；
- [ ] 规则基线与候选方法使用同一数据评估；
- [ ] 无标签结果没有被描述成恶意识别准确率。

### 输出与解释

- [ ] 每条记录有分数、等级、置信度和版本；
- [ ] 每条风险结论有证据或缺失说明；
- [ ] 等级映射到明确处置；
- [ ] 能展示原始聚合与修正聚合差异；
- [ ] 能查看典型误报和漏报。

### 工程与复现

- [ ] 依赖版本被锁定；
- [ ] 路径不依赖开发者个人电脑；
- [ ] 固定随机种子；
- [ ] 输出目录结构稳定；
- [ ] 每次运行保存配置与数据批次；
- [ ] 示例数据不包含敏感个人信息。

## 5. 解决方案成功标准

一个“像解决方案”的项目，不以页面数量为成功标准，而应满足：

1. 输入清楚：别人知道需要提供什么数据；
2. 过程清楚：别人知道系统如何处理；
3. 输出清楚：分数、等级和原因含义明确；
4. 行动清楚：不同等级对应可执行策略；
5. 效果可证：有基线、指标、错误案例和稳健性；
6. 边界诚实：规划能力不冒充已实现能力；
7. 能够复现：第三方可以按文档运行同一示例；
8. 能够迁移：更换数据源时只需字段映射和重新校准，而不是重写全部页面。

## 6. 实施路线图

### P0：恢复工程可用性

- 修复 Codex/终端环境；
- 完成仓库结构审计；
- 修复页面数据加载；
- 建立统一启动说明。

### P1：形成可演示解决方案

- 定义输入/输出 Schema；
- 固化示例数据和基线；
- 统一评分、等级和风险标签；
- 增加样本解释与处置模拟；
- 增加解决方案总览页；
- 提供一键演示脚本。

### P2：提高研究可信度

- 检查数据泄漏；
- 增加时间外验证与稳健性实验；
- 增加校准、误差切片和置信区间；
- 完成方法限制和伦理说明；
- 将所有图表与原始结果关联。

### P3：试点准备

- 提供字段映射模板；
- 支持客户脱敏样本批处理；
- 增加可配置阈值和版本记录；
- 增加运行日志、失败报告和数据漂移检查；
- 形成试点验收报告。
